# SPEC_AUDIT.md — Conformance audit of the Lean Wikifunctions formalization

**Repo:** Deicyde/wikifunctions (Lean 4 + Mathlib)
**Audited components:** `Wikifunctions/Core.lean`, `WikifunctionsEval.lean`, `Wikifunctions/Python/Imp.lean` (+ `Z13701.lean`, `Z13667.lean`, `*Prog.lean`, `native/`), `WikifunctionsSpecs.lean`
**Method:** every claim below was checked against (a) the canonical prose spec, (b) the machine-readable schemata, (c) the deployed orchestrator/evaluator source, and (d) the live wikifunctions.org API (`wikilambda_fetch` / `wikifunctions_run`, fetched 2026-07-02). Findings survived two adversarial verification passes; divergences in §3 are established, not suspicions.

---

## 1. The spec landscape

There is no single normative document. "The specification" is a stack of four layers with a clear normativity gradient:

| Layer | Where it lives | Normativity |
|---|---|---|
| **Function model** (prose: data model + evaluation model) | `wikifunctions.org/wiki/Wikifunctions:Function_model` — the canonical home. The mediawiki.org URL **does not exist** (API `missingtitle`); the Meta page is now an interwiki redirect. | Canonical statement of *intent*, but self-declaredly incomplete: Z7xx ZIDs are placeholders, examples still use the retired `Z10` (live fetch → Z550 Unknown reference), sum types / non-functional functions / Z16 native-value translation are deferred to unwritten documents, and evaluation order / implementation selection / validator behavior are *deliberately* left to the evaluator. |
| **function-schemata** (JSON-Schema YAMLs, `data/CANONICAL/`, `data/NORMAL/`) | `gitlab.wikimedia.org/repos/abstract-wiki/wikifunctions/function-schemata`; git submodule of the orchestrator, evaluator, and WikiLambda | The machine-enforced ground truth for representation: canonical vs normal form, the `^Z[1-9]\d*$` reference/string disambiguation, Benjamin arrays, the RESOLVER pattern (literal ≡ Z9 ≡ Z7 ≡ Z18 in any position), `Z14_literal`'s exactly-one-of Z14K2/K3/K4, the three-key Z22 envelope. |
| **Live built-in ZObjects + community types** | `wikifunctions.org` via `wikilambda_fetch` | Normative object definitions as deployed. Live is *richer* than the prose (Z4 has 8 keys, not 3; Z16K3 exists; error taxonomy Z500–Z599 lives in Meta's *Representation of errors* page). Community types the Lean models depend on — **Z13518** natural number (single key `Z13518K1 : Z6`, decimal string), **Z19677** rational (sign/numerator/denominator), **Z20838** float64, **Z16683** integer — are wiki content, not spec; only live fetches pin them. |
| **Deployed orchestrator/evaluator behavior** | `gitlab.wikimedia.org/.../function-orchestrator`, `function-evaluator`, helm values | Operational ground truth where the spec is silent: eager evaluation with a hardcoded lazy table (only builtin Z802's K2/K3 matter here); `FirstImplementationSelector` over a wiki-side speed-re-ranked Z8K4; errors as a Z5 under the `"errors"` key of the Z22K2 metadata map (Z22K1 = Z24 on failure); user Python runs on **RustPython 0.5.0 / wasm32-wasip1** under wasmtime with **10¹⁰ fuel**, 9 s evaluator / 9.7 s orchestrator deadlines; return values never type-checked (T429213); builtin Z1xx validators (incl. Z13518's Z101) skipped in production. |

**Consequence for this audit:** conformance is judged against layers 2–4 (schemata, live objects, deployed behavior); the prose Function model is used for concepts (Z18 key-id semantics, composition-is-any-ZObject, fixpoint evaluation) but never trusted over a live fetch.

## 3. Confirmed divergences

Deduplicated from 22 raw confirmed findings (independent auditors converged on D3, D4, D14, D15 twice each).

### Major

**D1. Z28925 Pythagorean-triple spec is order-sensitive; both live implementations are permutation-invariant.** `WikifunctionsSpecs.lean:362` defines `Z28925_spec a b c := decide (a*a + b*b = c*c)` in the given argument order, tags it `[faithful]` (:357), and bridges to Mathlib's order-sensitive `PythagoreanTriple` (:366-372). Live: composite **Z35061** sorts `[a,b,c]` ascending (via Z17873) before checking; Python **Z28926** conditionally swaps the max into K3. On input (5,4,3): Lean spec = `false`; both live impls = `True`. The Lean spec disagrees with **both** live implementations on every non-ascending permutation of a true triple. **Fix:** sort in the oracle (max as hypotenuse) or keep the ordered spec but document the a ≤ b ≤ c restriction and scope the `PythagoreanTriple` bridge accordingly; either way drop or qualify the `[faithful]` tag.

**D2. Z10862 multiply oracle is exact ℤ/ℚ arithmetic; all four live implementations are float64-lossy.** `WikifunctionsSpecs.lean:434` states `parse (Z10862_impl (render a) (render b)) = a * b` as oracle-testable ground truth. Live: Z12520/Z10864 (JS) do `parseFloat*parseFloat→toString`; Z12663 (Python) does `'%g' % (float*float)` — **6 significant digits**; Z31825 composes through Z20838 float64. `"0.1"×"0.2"` → live JS `"0.020000000000000004"` vs oracle 1/50; `"1234567"×"1"` → live Python `"1.23457e+06"`. The correspondence is false on a dense set of realistic inputs, the live impls disagree with *each other*, and neither the block nor `WIKIFUNCTIONS_SPECS.md:58` mentions float64. **Fix:** demote the ℤ/ℚ oracle to "mathematical intent", document the float64-exact regime where it matches live, and add an operational Float oracle (parse → Float mul → render) like the other float64 blocks.

### Minor — semantic edges visible in theorem statements

**D3. `.div` ÷0 totalization vs live Z28194 error.** `WikifunctionsEval.lean:93` uses Lean's total `Nat.div` (a/0 = 0); `lcmComposite_correct` (:140-142) quantifies over all a b, so it proves `some (.nat 0)` at (0,0). Live Z13546's impls all guard: Z13548 (Python) `if Z13546K2==0: Wikifunctions.Error("Z28194",…)`, likewise Z14084 (JS) and composite Z34175 — fetched and confirmed. Live `lcm(0,0)` via Z13661 reaches `divide(0,0)` (gcd(0,0)=0) and returns a Z5 error envelope, never 0. The header (:27-29) calls the leaves "correct by construction", which papers over exactly this edge; (0,0) is the *only* diverging input. **Fix:** return `none` on zero divisor (Option `none` *is* the model's Z5 channel) and restate the theorem with the (0,0) case split out, or document the totalization convention at the leaf and guard the theorem.

**D4. `.ratDiv` ÷0 totalization vs live Z28194 error.** Same class, larger diverging set: `WikifunctionsEval.lean:100` uses Mathlib's x/0 = 0; `bayesComposite_correct` (:171-173) has no `pB ≠ 0` hypothesis, proving `some (.rat 0)` on the entire pB = 0 hyperplane. Live Z19708 impls guard: Z20037 (JS) `if (Z19708K2.K1===0n){ Wikifunctions.Error("Z28194",…)`, Z19710 (Python) `if Z19708K2==0: …` — fetched and confirmed. **Fix:** `none` on zero divisor plus `(hpB : pB ≠ 0)` on the theorem, or an explicit convention note.

**D5. Imp `%` by zero: Lean total (`x % 0 = x`), Python raises.** `Imp.lean:99` evaluates `.mod` with total `Nat.mod` (probed: `5 % 0 = 5`); CPython and RustPython 0.5.0 raise `ZeroDivisionError` → live Z507. The trust note (:29-37) claims faithfulness for "`%` on non-negative integers", which as written includes divisor 0 and is therefore false. Mitigating: structurally unreachable in both deployed programs — Z13701's `%` executes only under the `while Z13701K2 != 0` guard evaluated in the *same* state (`Stmt.run`, Imp.lean:122-131); Z13667 uses no `%`. No current theorem affected, but a future unguarded `%` would silently verify against wrong semantics. **Fix:** carve out "positive divisor" in the trust note (with the guard argument), or make `.mod` Option-valued.

**D6. Z28925 zero-guard: the two live impls disagree with each other; the Lean spec silently sides with one.** `WikifunctionsSpecs.lean:362`: spec is true at (0,0,0) and (0,n,n). Live Z28926 (Python) opens with `if any input == 0: return False`; Z35061 (composite) has no guard and matches the equation. On (0,3,3): Lean `true`, Z35061 `true`, Z28926 `False`. Undocumented. **Fix:** doc note that the spec follows the pure equation (= Z35061) and that Z28926 additionally rejects zeros — live is internally inconsistent there.

**D7. Z13341 lerp: live Python impl is partial on t ∉ [0,1].** `WikifunctionsSpecs.lean:576`'s total spec `(1.0 - t) * a + t * b` is bit-exact against JS Z31184 and composite Z34167 (verified), but Python Z13342 `return None` for t outside [0,1] → live error envelope (Lean at (10,20,2.0): `30.0`; live via Z13342: error). **Fix:** doc note scoping the operational-exactness claim to Z31184/Z34167.

**D8. Z21005 log10: oracle computes a different float function than live.** `WikifunctionsSpecs.lean:523` uses `Float.log x / Float.log 10.0` under the header's "bit-for-bit #eval-comparable" claim (:17-19; `WIKIFUNCTIONS_SPECS.md:5`); live uses native log10 (JS `Math.log10` in Z22341, Python `math.log10` in Z21019). At x = 1000: native log10 = exactly `3.0`; `Float.log 1000 / Float.log 10` = `2.9999999999999996`. The file's own `#guard` at :526 already needs a 1e-9 tolerance, contradicting the header. **Fix:** hedge to "≤1–2 ULP, compare with tolerance", or bind libm `log10` via `@[extern]`.

### Minor — proof-artifact wiring and harness

**D9. The proved Z13701 program and the executed/difftested one are formally unrelated twins.** `Z13701.lean:44-59,136-139` *restates* (does not import) `Z13701Prog.lean:24-46`; `DiffDriver.lean` imports only the Prog twin. Verified: co-importing both fails (`environment already contains Wikifunctions.Python.varA`), so no Lean module can ever connect `runProgram_eq_coprime` to the binary being differentially tested. Today the twins are token-identical (behavior coincides; 859/0 on the corrected harness), but any future edit desynchronizes them silently. `Z13701Prog.lean:8`'s "which imports this" is factually false, and the lakefile comment ("importing both would collide") is contradicted by the Z13667 pair, where `Z13667.lean` imports `Z13667Prog` cleanly. **Fix:** make `Z13701.lean` import `Z13701Prog` and delete the restatement (the demonstrably-building Z13667 pattern); fix both stale comments.

**D10. The empirical trust-discharge harness cannot run as committed.** `native/difftest.py:22` computes `LEAN_DIR = native/../lean`, a path that ceased to exist when commit 4504464 flattened the layout out of WikiLean; the diffdriver binary actually lives at `<repo-root>/.lake/build/bin/diffdriver` (verified: `subprocess.run` would raise `FileNotFoundError`). `DiffDriver.lean:5-7`'s "`../native/difftest.py`" is likewise stale, as are paths in `native/README.md` and `native/leanpy/README.md`. With paths corrected, the check *passes*: 859 cases (incl. consecutive-Fibonacci worst-case Euclid pairs), 0 mismatches, 0 fuel exhaustions. **Fix:** point `LEAN_DIR` at the repo root; fix the three stale comments/docs.

### Minor — trust-anchor scope (Python embedding)

**D11. The trust assumption is anchored to CPython; the deployed runtime is RustPython 0.5.0 on wasm.** `Imp.lean:31-37` (echoed at `Z13701.lean:37-39`, `Z13667.lean:41-43`, `native/difftest.py:5-9`) claims faithfulness to CPython, dischargeable by running CPython. Deployed user Python runs under RustPython 0.5.0 compiled to wasm32-wasip1 inside wasmtime (function-evaluator, verified). The unstated lemma "RustPython ≡ CPython on this subset" is what actually connects the proofs to production; on the constructs used it holds, but no in-target file mentions RustPython/wasm (grep: zero hits), and the one out-of-target acknowledgment (`native/README.md`) cites a Verus artifact `rustpython_int_floordiv.rs` that is **absent from the repo** (only `z13701_coprime.rs` exists). **Fix:** amend the trust note; commit or drop the Verus artifact.

**D12. The ℕ-typed theorems assume an input precondition that production enforces only weakly.** `Z13701.lean:143-144`, `Z13667.lean:144` quantify over ℕ, implicitly assuming deployed code receives naturals. Live, Z13518's Python converter Z13531 is `int(...['Z6K1'])` on an arbitrary string and the builtin validator **Z101 is skipped in production** — a crafted `{"Z13518K1":"-5"}` delivers a genuine negative int to Z29182/Z13668, outside the verified domain (deployed Z13701(-1,0) → False via floor-mod; Z13668 → 1 via empty range). Non-numeric strings fail in the converter (Z507) before the body, consistent with the model's scope. **Fix:** one header sentence per proof file stating the well-formed-Z13518 precondition and the weak live enforcement.

**D13. The ∀n factorial claim ignores the platform's binding resource limits.** `Z13667.lean:8-10,142-148` claims the deployed implementation "computes exactly Nat.factorial" for all n. The platform bounds every execution: wasmtime fuel 10¹⁰ (exhaustion → **Z576**), 9 s evaluator / 9.7 s orchestrator deadlines, 640 MiB. Large-n live factorial returns Z576/timeout, not n!. Ironic inversion: the model's internal fuel (n+1) is *proved* non-binding, while the platform's fuel is the actual behavior at scale; no in-target doc mentions timeouts/Z576. Z13701 is immune in practice (Euclid is logarithmic). **Fix:** scope the headline claim: "…whenever the platform's resource limits are not exhausted; the theorems characterize language semantics, not the execution budget."

### Minor — documentation and taxonomy

**D14. `WikifunctionsEval.lean:18` cites the nonexistent ZID Z70 as the rational type.** Live fetch of Z70 → Z550 Unknown reference. The rational type actually used by Z20000/Z19706/Z19708 is **Z19677** (Z19677K1 sign : Z16659, Z19677K2 numerator : Z13518, Z19677K3 denominator : Z13518). The ℚ modelling itself is right; only the citation is wrong (Core.lean:19 avoids it). **Fix:** "Z19677 rationals (sign/numerator/denominator record, modelled up to rational equality as ℚ)".

**D15. Bayes argument labels are transposed vs live Z20000.** Live: Z20000K1 = P(A), K2 = P(B|A), K3 = P(B); Z20001 computes `Z19708(Z19706(K1,K2), K3)`. `WikifunctionsEval.lean:166` writes `divide(multiply(P(B|A), P(A)), P(B))` and :171-172 binds `env [pBA, pA, pB]` — AST and argument *order* are exact (verified), and multiplication commutes, so every theorem is numerically correct, but a reader gets K1/K2 semantics backwards. Same transposition in `WikifunctionsSpecs.lean:335` (info). **Fix:** rename binders to `(pA pBA pB)`, fix both docstrings.

**D16. Positional Z18 encoding is sound but stated nowhere.** `Core.lean:29` (`arg : Nat`) and `WikifunctionsEval.lean:83` resolve Z18 by `env[i]?`. A real Z18 references by *key-id string* (`{"Z1K1":"Z18","Z18K1":"Z13701K1"}`); only transient functions are positional. Verified node-for-node that in all six live bodies every Z18 references the enclosing function's densely-numbered keys and every theorem binds env in key order — the bijection `arg i ↦ ZxK(i+1)` is exact here — but the abstraction is documented in none of Core.lean, WikifunctionsEval.lean, README.md, WIKIFUNCTIONS_SPECS.md (grepped). **Fix:** one docstring sentence at `Expr.arg`.

**D17. `Core.lean:27` overclaims that `Expr` "is the shape of a Z14K2 composite body".** A real Z14K2 is *any* ZObject (declared type Z1): computed callees (Z7K1 itself a call/Z18/inline Z8, per the schemata RESOLVER pattern), constructor-style literals whose fields embed calls (live Z30841), whole-body list literals (Z21920), Z9 function references as argument values (Z31679 passes Z13701 to Z13436), Z99 quotes. The recursion/higher-order gaps *are* documented well (:35-50), and none of the six modelled composites exercises the rest — but the excluded forms are unlisted. **Fix:** soften to "the fragment the modelled composites use" and enumerate exclusions.

**D18. Z20000 sits in the wrong tier of WikifunctionsSpecs.lean.** :333 places Bayes in tier-1 "composite_provable — computable/decidable ℕ/ℤ oracle; provable in-kernel" (:13-14), but `Z20000_spec : ℚ → ℚ → ℚ → ℚ` (:343) is exactly what the file's *own* tier-2 definition (:15-16) covers; its concrete check (:353) uses `norm_num`, not kernel `decide`. Also inherits the undocumented pB = 0 totalization (cf. D4; the analogous Z30840 block *does* document its convention). **Fix:** move the block to tier 2 (or widen tier 1's definition) and add the ÷0 note.

## 5. Refuted / downgraded suspicions

**Refuted (2):**
- `.dec` at 0 suspected divergent (raw Python `n-1` → −1): **refuted by direct fetch** — all three live Z13582 impls explicitly truncate (Z13586, Z13914, Z13583); the leaf is faithful and `simplexComposite_correct` holds at r = 0.
- `.ite` branch-type permissiveness suspected unsound: **refuted on the material point** — Z13846 ("if (natural number output)", Z40×Z13518×Z13518→Z13518) is the correct counterpart of the `.ite` leaf; the broader-than-declared branch typing (:96) is only ever instantiated at nat branches and live enforcement is absent anyway (Z101 skipped; returns unchecked, T429213).

**Downgraded to info (15), one line each:**
- Option collapse of the Z22/Z5 error taxonomy and live deferred-error-propagation: documented at Core.lean:40-42, unobservable on the success-path theorems.
- Eager left-to-right `evalArgs` vs live Promise.all/lazy-table: unobservable in the Option universe; the one lazy-load-bearing case (Z802) is declared out of scope.
- `Val.rat : ℚ` quotients unreduced Z19677 representations; `.ite` accepts any Val branches: standard abstractions, no provable statement affected.
- Core.lean:6-10's "nothing baked into a closed enum" registry story is aspirational — no module registers a denotation; WikifunctionsEval uses a closed `Leaf` enum, and the two files define clashing `Wikifunctions.Val/Expr/eval` duplicates.
- Positional-arg + ℚ-quotient abstractions (composites): deliberate, verified sound for all six composites.
- `State.get` unbound-read-defaults-to-0 (Imp.lean:50-52): documented, unreachable in both programs; worth one line in the trust note.
- Docstring whitespace vs deployed sources (tabs, `k=1`); "1:1 transcription" is fair only at AST level for the for→while desugaring.
- `native/leanpy/Main.lean:19-27` alpha-renames parameters (not "the exact deployed" source) and `native/README.md:37`'s `rustpython_int_floordiv.rs` does not exist in the repo.
